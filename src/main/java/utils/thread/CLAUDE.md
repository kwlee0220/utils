# utils.thread

Concurrency utilities sitting between `java.util.concurrent` and [utils.async](../async/CLAUDE.md): the canonical lock+condition wrapper, recurring schedulers, executor wrappers, and inter-thread hand-off channels. User-facing guide: [README.md](README.md).

**`Guard` is the load-bearing type here** — 12 files inside this library and ~30 in the downstream MDT projects use it. The rest are standalone utilities with little or no in-library usage; treat them as available tools, not as assumed infrastructure.

## Guard — the standard lock+condition pattern

One `ReentrantLock` + one `Condition`, created via `Guard.create()`. Two usage modes plus a low-level escape hatch.

- **Work mode** — `run(Runnable)`, `get(Supplier)`, `accept(Consumer,T)` and their `Checked*X` variants (`runChecked`, `getChecked`, `acceptChecked`). Acquires the lock, runs the body, and calls `signalAll()` in `finally` before unlocking. **`get()` signals too**, even though it is nominally a read. `read(Supplier)` locks without signalling — use it for plain reads and **always inside condition predicates**: a `get()` there makes waiters wake each other on every check and spin with no state change. Keep `get()` when the supplier mutates state.
- **Condition-wait mode** — `awaitCondition(pred)` (`pred` is a `BooleanSupplier` — no boxing per evaluation, no NPE from a `null` result; a `Supplier<Boolean>` *variable* must be passed as `sup::get`) → `AwaitCondition`, or `awaitCondition(pred, due|Duration|(timeout,unit))` → `TimedAwaitCondition`. Terminals: `andReturn()`, `andRun(task)`, `andRunChecked(task)`, `andGet(supplier)`, `andGetChecked(supplier)`. They take the lock via `lockForWait()`: `tryLock()` first (so an already-interrupted thread still proceeds when the lock is free and the condition holds), else `lockInterruptibly()` — interrupting a thread blocked on the lock throws `InterruptedException` and skips the task. Timeouts never cover the lock wait. `Duration`s beyond the nanosecond range saturate to `Long.MAX_VALUE` (`toNanosSaturated`, also in `awaitSignal(Duration)`; `Duration.toNanos()` would throw `ArithmeticException` even when the condition already held). The `Date` builder copies the due date and compares `due <= now` directly (no subtraction, so `new Date(Long.MIN_VALUE)` cannot overflow). The timed variants throw `TimeoutException` (immediately if `timeout == 0` and the condition is unmet); both the `Date` and the `Duration` forms re-check the condition after the deadline wake-up before timing out. `InterruptedException` from the wait or from a `*Checked` task is rethrown **without** re-setting the interrupt flag (in every wait form, timed or not). `andRunChecked`/`andGetChecked` wrap task failures in `ExecutionException` (unwrapped cause) except `InterruptedException` (rethrown) and `VirtualMachineError` (rethrown unwrapped, via `toExecutionException`); other `Error`s such as `AssertionError` are still wrapped.
- **Builder structure**: `AwaitCondition` and `TimedAwaitCondition` both extend the sealed `AbstractAwaitCondition<X extends Exception>`, which implements the five terminals once. Subclasses only implement `awaitPrecondition(guard, pred)`. `X` is the wait-failure exception: `RuntimeException` for `AwaitCondition` (so its terminals still declare no `TimeoutException`), `TimeoutException` for the timed one. Terminals reject a `null` task/supplier with `IllegalArgumentException` **before** taking the lock; so do `run`/`runChecked`/`read`/`get`/`getChecked`/`accept`/`acceptChecked`. `PreAction` is `final` and its `m_guard` private.
- **`preAction(Runnable)`** — chains a one-shot action that runs under the lock just before the condition is first evaluated (e.g. send the request, then wait for the response). `signalAll()` fires right after it, whether it returned or threw (the exception then propagates) — so waiters for the state it changed wake up (otherwise a request registered in a `preAction` could leave both the requester and the responder waiting).
- **Low-level** — `lock()`/`unlock()`, `signalAll()`, `awaitSignal()`, `awaitSignalUntil(Date)` (deadline), `awaitSignal(Duration)` (period), `awaitSignalNanos(long)`. Caller owns lock pairing and signal placement.

Predicate polarity: `Guard.awaitCondition(pred)` loops `while (!pred)` — it waits **until** the predicate is true.

`awaitCondition(...).andReturn()` waits but does **not** signal; `andRun`/`andGet` signal after the task. Mutating shared state after `andReturn()` leaves waiters asleep — use `andRun` instead.

Convention across the repo: a `private final Guard m_guard = Guard.create();` field with `@GuardedBy("m_guard")` on the state it protects. `EventDrivenExecution` exposes its guard as the protected `m_aopGuard`.

## ConditionVariable — inverted polarity

`ConditionVariable(Condition, Supplier<Boolean> waitCond)` loops `while (waitCond)` — the predicate is a **wait** condition, the opposite of `Guard.awaitCondition`. `await()`, `await(time, unit)`, `awaitUntil(deadline)`; the caller holds the lock. Prefer `Guard` in new code; mixing the two polarities silently produces "returns immediately" or "waits forever" bugs.

## Recurring execution

`RecurringWork` = `onStarted(schedule)` / `perform()` / `onStopped()`. `InterruptibleWork` adds `interrupt()` for work that provides its own cancel path.

One `RecurringSchedule` implementation (there is no pool-based variant; use a JDK `ScheduledExecutorService` for pool-based periodic work):

| Impl | Threading | Timing |
| --- | --- | --- |
| `RecurringScheduleThread` | dedicated thread | Static factories `newFixedRateSchedule` / `newFixedDelaySchedule` (with or without `initialDelay`). Fixed-rate subtracts elapsed `perform()` time from the interval, logs `late schedule` on overrun, and compensates sleep overhead via `utils.LongVariableSmoother`. Fixed-delay sleeps the full interval after each run. `getState()` reports `STOPPED` before start and `WORKING` during `perform()`; `start()` throws `ExecutionException` when `onStarted()` fails (`m_startFailed` tells it from a fast first-`perform()` failure); `stop()` before start goes straight to `STOPPED` without `onStopped()`. `stop()` never waits: during `onStarted()` it marks `STOPPING` and returns (`start()` waits on `m_startCompleted`, not on the state), and the worker then skips `perform()` and calls `onStopped()` only if `onStarted()` succeeded — so a self-stop from `onStarted()` is safe. `InterruptibleWork.interrupt()` / `Thread.interrupt()` are requested **outside** the lock, at most once (`m_interruptRequested`; a later `stop(true)` can still escalate a `stop(false)`), and not when the worker thread stops itself. The wait loop waits for a deadline (`dueNano`) and distinguishes deadline / `performNow()` (`m_runNowRequested`) / stop; only a wait that actually reached the deadline feeds the fixed-rate overhead smoother, and other wake-ups re-wait the remainder. `performNow()` returns `true` only when it was accepted (IDLE). Interval/initialDelay are validated (`interval > 0`, `initialDelay >= 0`, also in `setInterval()`), nanos via saturating `TimeUnit.toNanos`, and time comparisons use differences so huge intervals do not overflow. Fixed-rate does not catch up missed runs; `setInterval()` applies from the next wait. Used by marmot (`start()` / `stop(true)` only). |

**Time values are `Duration`**: `getInterval()` returns `Duration`, `setInterval(Duration)`, `waitForStopped(Duration)`, and `RecurringScheduleThread.newFixedRate/DelaySchedule(name, work, [initialDelay,] interval)` take `Duration` (interval ≥ 1 ms, initialDelay ≥ 0, values beyond `long` ms saturate). The `long`-millisecond factories, `setInterval(long)` and `waitForStopped(long)` remain as `@Deprecated` delegates (the latter two as interface default methods) because marmot calls the factories and is not on this machine — user decision to keep them until marmot is migrated. Internally the schedule still stores milliseconds.

Shared control surface: `getState()` (`STARTING`/`WORKING`/`IDLE`/`STOPPING`/`STOPPED`), `getFailureCause()`, `getInterval()`/`setInterval(Duration)` (live-updatable), `performNow()` (requests an immediate iteration of an IDLE schedule; returns whether the request was accepted), `start()`, `stop(mayInterruptIfRunning)`, `waitForStopped()`/`waitForStopped(Duration)`.

`stop()` returns before `onStopped()` necessarily ran — chain `waitForStopped()` when cleanup must be complete. Calling `waitForStopped()` from inside `perform()` on your own schedule throws `IllegalStateException` (deadlock guard).

## Executors

- **`ExecutorAware`** — `getExecutor`/`setExecutor`; the container injects after property setup and before `Initializable.initialize()`.
- **`AsyncConsumer<T> implements Consumer<T>`** — pushes consumption onto a pool. `singleWorker(consumer[, executor])`, `multipleWorkers(statelessConsumer, nThreads)`, `from(statelessConsumer, executor)`. `accept()` is fire-and-forget; `schedule()` returns a `CompletableFuture<Void>`. The multi-worker factories require a **stateless** consumer.
- **`SingleWaiterExecutor`** — at most one running `StartableExecution` plus a single pending slot. A new `submit` while one is running `cancel(true)`s whatever was pending and takes its place (latest-wins). Not an `Executor`; fire-and-forget, so track completion via the execution's own finish callbacks. The lock only decides slots — `start()` and `cancel(true)` run **outside** the guard (avoids lock-order inversion with the job's own lock); `launch()` registers `whenFinishedAsync(onDone)` before `start()`, and if `start()` throws (without finishing the job, so no finish callback would come) it calls `onDone(exec)` itself to vacate the running slot and start the pending job — the exception is rethrown to the `submit()` caller, or only logged when the job was chained from `onDone`. `shutdownNow()` plus `isShutdown()`: it cancels each job in its own `try` and rethrows the first failure with the rest suppressed (so a throwing pending-job cancel does not skip the running job). A replaced pending job whose `cancel` throws is only logged — the new job was already accepted. Re-submitting a job that is running or pending → `IllegalArgumentException`. A job whose `start()` throws without finishing is `cancel(true)`ed by the executor so its finish callbacks always fire (result: CANCELLED, not FAILED — `StartableExecution` has no failure API). No worker thread: the first job's `start()` runs on the `submit` caller, later ones on the previous job's finish-callback thread, so `submit()` may not return quickly. Tests: `SingleWaiterExecutorTest` (9).
- **`CallerRunsSerialExecutor`** — `Executor` that runs tasks one at a time in FIFO order **without its own thread**: whichever thread enqueues while no one is draining becomes the dispatcher and drains the queue, including tasks other threads add meanwhile. `execute` (fire-and-forget, failures only logged), `submit(Callable)` / `submit(Runnable)` (→ `CompletableFuture`), `invokeOrDefer` (waits, unless waiting would deadlock — the caller is the dispatcher, or holds the optional `outerLock` while another thread drains — in which case it only enqueues; returns an `Invocation`: `isDeferred()`, `completion()`, and `get()` which, for a non-deferred call, rethrows the task's **original** exception — a `CompletionException` the task threw itself is not unwrapped, which is why `Task` records the failure beside the future. Deferred ≠ not run: resending runs the task twice). Cancelling a returned future does not stop the task; a task whose future is already done when it reaches the head of the queue is skipped (best-effort). `runAsDispatcher` (advanced; bypasses the queue: waits for the dispatcher role, runs the task on the caller thread, then drains what queued meanwhile; rejects a caller holding `outerLock`. **Can starve** — the dispatcher only lets go when the queue is empty, and nothing hands the role to a waiter. **Called from the dispatcher it runs inline, nested inside the current task**, ahead of everything queued). Javadoc lists the costs (dispatcher can be held long, no thread affinity, non-async future callbacks registered before completion run on the dispatcher — but callbacks registered after completion, or fired by a caller completing/cancelling the future, run elsewhere, so never assume callbacks are inside the serial order) and the differences from Guava `MoreExecutors.newSequentialExecutor(directExecutor())` — use Guava when plain fire-and-forget ordering is enough. `StateChart`'s signal queue is built on it (outer lock = the chart lock; `postSignal` returns `submit(...).copy()` so callers cancelling or timing out the future cannot drop a signal — do the same wherever a submitted task must run regardless of what the caller does with its future).
- **`Timer`** — backs `Execution.setTimeout` (`EventDrivenExecution.setTimeout` → `Executions.getTimer()`, a lazily created holder singleton that is never shut down). `setTimer(execution, timeout, unit)` / `setTimer(execution, Date)` return a `Timer.TimeoutHandle` that represents only the **schedule**: `cancel()` unschedules (never cancels the execution), `isPending()` / `isCancelled()` / `isExpired()` (expired = the `cancel(true)` request was handed to the canceller; it does not mean it ran or that the execution finished). Re-scheduling the same execution **adds** a timer; extend a deadline by cancelling the old handle first. Implementation: a 1-thread daemon `ScheduledThreadPoolExecutor` with `setRemoveOnCancelPolicy(true)` only measures time and hands expiry to a bounded daemon "canceller" pool (`MAX_CANCELLATION_THREADS` = 4, unbounded queue, idle threads time out; no `CallerRunsPolicy`, which would run cancels on the scheduler again), which calls `exec.cancel(true)` if not done (a rejected cancel is logged at DEBUG with the state — it can race a normal finish) — so a slow cancel never blocks time-keeping; past 4 blocked cancels, later ones queue and no timer lock is held while waiting for an execution's lock. `exec.whenFinished(r -> future.cancel(false))` releases the timer as soon as the execution finishes (a sync listener is fine: `cancel(false)` only removes from the queue). Monotonic time; the `Date` overload converts to a delay at registration (past dates, including `Long.MIN_VALUE`, become 0 without overflow). `shutdown()` cancels every pending handle (`shutdownNow()` only drains the queue without completing the futures); `setTimer` after `shutdown()` → `IllegalStateException`. The `whenFinished` listener the timer registers is not retained after the execution finishes (`EventDrivenExecution` clears its finish listeners after notifying and does not store listeners added after completion). Threads are named `execution-timer-N` / `execution-timer-cancel-N`. There is no cap on pending timers, finished executions leave the queue immediately, and `cancel(true)` never runs under a timer lock. Tests: `utils.async.TimerTest`.

## Inter-thread hand-off

- **`SingleSlotOverwriteQueue<T>`** — length-1, latest-wins: `add` overwrites an unconsumed item with no notification. `add` rejects `null` (it is the empty sentinel). Retrieval follows `BlockingQueue` conventions: `take()` blocks, `poll()` never waits for an item and returns `null` when empty, `poll(Duration)` returns `null` on timeout (the timeout covers waiting for an item, not acquiring the lock — the critical section is one field access); `peek()` is non-destructive, may return `null`, and uses `read()` (no signal). Implemented on Guard's low-level API (`lock`/`awaitSignal`/`awaitSignalNanos`/`unlock`): **interrupt wins** — `take()`/`poll(Duration)` check `Thread.interrupted()` on entry and throw `InterruptedException` even if an item is present, leaving it (JDK `BlockingQueue` policy; Guard's `tryLock`-first terminals would have returned the item), `poll()`/`peek()` ignore interrupts; only `add()` signals (removing an item never satisfies a waiter). It does not implement `Queue`. Tests: `SingleSlotOverwriteQueueTest`. Use for coalescible values (sensor samples, progress); use a `BlockingQueue` when no event may be lost.
- **`CompletionFStream<T> implements TimedFStream<Result<T>>`** — consume results of executions in **completion order**; elements are `Result<T>` (failures/cancellations are elements, not exceptions). It **wraps** a `SuppliableFStream` rather than extending it, so `supply`/`endOfSupply`/`poll` are not public. Registration API: `register(Execution)` collects only (caller starts; any state accepted — finished or pre-start-cancelled executions are collected immediately), `submit(StartableExecution)` requires `isNotStarted()` and starts it (the stream owns the start; a `start()` that throws without finishing → `cancel(true)` so a result still arrives, then rethrow), `submit(Callable, Executor)`. **Capacity = max registered-but-not-yet-consumed executions**: registration waits (caller thread, no lock held; hence `throws InterruptedException`) when reached, so the buffer can never be full when a completion callback supplies (`supply(r, 0, ms)`; a timeout is logged as a bug) — the callback, which runs under the execution's `m_aopGuard`, never blocks, and no delivery thread/unbounded queue is needed. Termination: `finishSubmissions()` rejects further registrations and ends the stream after **all registered** results are delivered (`m_undelivered` reaches 0); `close()` discards buffered and later results, wakes waiting registrants with ISE, does not cancel executions, and later `next()` returns empty. Registering and consuming on the same thread beyond capacity deadlocks — produce on another thread. Tests: `CompletionFStreamTest` (14).
- **`CoalescingSupplier<T> implements CheckedSupplier<T>`** — call coalescing, **not memoization**. Concurrent `get()` calls share one in-flight computation (result or exception); non-overlapping calls each recompute. For real caching use `utils.func.Lazy` / `TimedLazy`. API: `get()` (waits without limit; no `TimeoutException`) and `get(Duration joinTimeout)` (per call; bounds only the wait for another thread's production, never the producing call; values beyond the nanosecond range saturate to `Long.MAX_VALUE` ns). Each production gets its own `CompletableFuture` (`m_inFlightResult`, cleared by `clearInFlightIfCurrent()` under the guard **before** it is completed, so later callers start a new production): waiters get exactly the production they joined, `null` results are shared, and every caller gets the same object. A failure reaches every caller as `ExecutionException` with the same cause — including a `CancellationException` thrown by the source (`CompletableFuture.get()` would rethrow it unwrapped, so the wait path wraps it); the producer gets `InterruptedException` if it was itself interrupted; a `VirtualMachineError` is rethrown after waiters are completed. **Reentrant calls** (the source calling the same supplier) are rejected with `IllegalStateException` (`m_producerThread`), since they would wait for their own result. `getWaitingCount()` (package-private) reports blocked waiters via `getNumberOfDependents()`; tests synchronize on it instead of sleeping. Tests: `CoalescingSupplierTest`.

## Conventions

- Argument validation uses `utils.Preconditions`. `ConditionVariable` still imports Guava `Preconditions` — new code should not.
- Fields protected by a `Guard` carry `@GuardedBy("m_guard")`.
- Classes that log implement `utils.LoggerSettable` (`RecurringScheduleThread`, `SingleWaiterExecutor`, `CoalescingSupplier`).
- Korean Javadoc dominant; preserve language when modifying.
- Tests exist only for `Guard`, `CompletionFStream`, `CallerRunsSerialExecutor`, `CoalescingSupplier` and `RecurringScheduleThread` (`src/test/java/utils/thread/`), plus `Timer` in `utils.async.TimerTest`. Changes elsewhere in this package are unguarded by tests.

## Common gotchas

- `signalAll()` called outside the lock throws `IllegalMonitorStateException`. Work mode and `andRun`/`andGet` handle it for you.
- `andReturn()` does not signal — see above.
- `Guard.get()` signals on every read.
- `RecurringSchedule.stop()` is a request, not a join.
- `SingleSlotOverwriteQueue` drops events by design.
