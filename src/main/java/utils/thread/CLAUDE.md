# utils.thread

Concurrency utilities sitting between `java.util.concurrent` and [utils.async](../async/CLAUDE.md): the canonical lock+condition wrapper, recurring schedulers, executor wrappers, and inter-thread hand-off channels. User-facing guide: [README.md](README.md).

**`Guard` is the load-bearing type here** — 12 files inside this library and ~30 in the downstream MDT projects use it. The rest are standalone utilities with little or no in-library usage; treat them as available tools, not as assumed infrastructure.

## Guard — the standard lock+condition pattern

One `ReentrantLock` + one `Condition`, created via `Guard.create()`. Two usage modes plus a low-level escape hatch.

- **Work mode** — `run(Runnable)`, `get(Supplier)`, `accept(Consumer,T)` and their `Checked*X` variants (`runChecked`, `getChecked`, `acceptChecked`). Acquires the lock, runs the body, and calls `signalAll()` in `finally` before unlocking. **`get()` signals too**, even though it is nominally a read. `read(Supplier)` (added 2026-10-31) locks without signalling — use it for plain reads and **always inside condition predicates**: a `get()` there makes waiters wake each other on every check and spin with no state change. Keep `get()` when the supplier mutates state.
- **Condition-wait mode** — `awaitCondition(pred)` → `AwaitCondition`, or `awaitCondition(pred, due|Duration|(timeout,unit))` → `TimedAwaitCondition`. Terminals: `andReturn()`, `andRun(task)`, `andRunChecked(task)`, `andGet(supplier)`, `andGetChecked(supplier)`. They take the lock via `lockForWait()`: `tryLock()` first (so an already-interrupted thread still proceeds when the lock is free and the condition holds), else `lockInterruptibly()` — interrupting a thread blocked on the lock throws `InterruptedException` and skips the task (it used plain `lock()` before 2026-10-31). Timeouts never cover the lock wait. `Duration`s beyond the nanosecond range saturate to `Long.MAX_VALUE` (`toNanosSaturated`, also in `awaitSignal(Duration)`; `Duration.toNanos()` used to throw `ArithmeticException` even when the condition already held). The `Date` builder copies the due date and compares `due <= now` directly (a subtraction overflowed for `new Date(Long.MIN_VALUE)` and spun forever). The timed variants throw `TimeoutException` (immediately if `timeout == 0` and the condition is unmet); both the `Date` and the `Duration` forms re-check the condition after the deadline wake-up before timing out (the `Date` form used to throw as soon as `awaitSignal(due)` returned `false`). `InterruptedException` from the wait or from a `*Checked` task is rethrown **without** re-setting the interrupt flag (before 2026-10-31 the timed waits and `*Checked` terminals set it again and threw — a double signal the unbounded waits never did). `andRunChecked`/`andGetChecked` wrap task failures in `ExecutionException` (unwrapped cause) except `InterruptedException` (rethrown) and `VirtualMachineError` (rethrown unwrapped, via `toExecutionException`); other `Error`s such as `AssertionError` are still wrapped.
- **`preAction(Runnable)`** — chains a one-shot action that runs under the lock just before the condition is first evaluated (e.g. send the request, then wait for the response). `signalAll()` fires right after it, whether it returned or threw (the exception then propagates) — so waiters for the state it changed wake up; before 2026-10-31 it signalled only on failure, and a request registered in a `preAction` could leave both the requester and the responder waiting.
- **Low-level** — `lock()`/`unlock()`, `signalAll()`, `awaitSignal()`, `awaitSignal(Date|Duration)`, `awaitSignalNanos(long)`. Caller owns lock pairing and signal placement.

Predicate polarity: `Guard.awaitCondition(pred)` loops `while (!pred)` — it waits **until** the predicate is true.

`awaitCondition(...).andReturn()` waits but does **not** signal; `andRun`/`andGet` signal after the task. Mutating shared state after `andReturn()` leaves waiters asleep — use `andRun` instead.

Convention across the repo: a `private final Guard m_guard = Guard.create();` field with `@GuardedBy("m_guard")` on the state it protects. `EventDrivenExecution` exposes its guard as the protected `m_aopGuard`.

## ConditionVariable — inverted polarity

`ConditionVariable(Condition, Supplier<Boolean> waitCond)` loops `while (waitCond)` — the predicate is a **wait** condition, the opposite of `Guard.awaitCondition`. `await()`, `await(time, unit)`, `awaitUntil(deadline)`; the caller holds the lock. Prefer `Guard` in new code; mixing the two polarities silently produces "returns immediately" or "waits forever" bugs.

## Recurring execution

`RecurringWork` = `onStarted(schedule)` / `perform()` / `onStopped()`. `InterruptableWork` adds `interrupt()` for work that provides its own cancel path.

Two `RecurringSchedule` implementations:

| Impl | Threading | Timing |
| --- | --- | --- |
| `RecurringScheduleThread` | dedicated thread | Static factories `newFixedRateSchedule` / `newFixedDelaySchedule` (with or without `initialDelay`). Fixed-rate subtracts elapsed `perform()` time from the interval, logs `late schedule` on overrun, and compensates sleep overhead via `utils.LongVariableSmoother`. Fixed-delay sleeps the full interval after each run. `getState()` reports `STOPPED` before start and `WORKING` during `perform()`; `start()` throws `ExecutionException` when `onStarted()` fails (`m_startFailed` tells it from a fast first-`perform()` failure); `stop()` before start goes straight to `STOPPED` without `onStopped()`. `stop()` never waits: during `onStarted()` it marks `STOPPING` and returns (`start()` waits on `m_startCompleted`, not on the state), and the worker then skips `perform()` and calls `onStopped()` only if `onStarted()` succeeded — so a self-stop from `onStarted()` is safe. `InterruptableWork.interrupt()` / `Thread.interrupt()` are requested **outside** the lock, at most once (`m_interruptRequested`; a later `stop(true)` can still escalate a `stop(false)`), and not when the worker thread stops itself. The wait loop waits for a deadline (`dueNano`) and distinguishes deadline / `performNow()` (`m_runNowRequested`) / stop; only a wait that actually reached the deadline feeds the fixed-rate overhead smoother, and other wake-ups re-wait the remainder. `performNow()` returns `true` only when it was accepted (IDLE). Interval/initialDelay are validated (`interval > 0`, `initialDelay >= 0`, also in `setInterval()`), nanos via saturating `TimeUnit.toNanos`, and time comparisons use differences so huge intervals do not overflow. Fixed-rate does not catch up missed runs; `setInterval()` applies from the next wait. Fixed 2026-10-31 together with an inverted `setLogger()` and a `waitForStopped(long)` that threw outside `try` and leaked the lock; before that, `stop()` called `interrupt()` under the lock (deadlock if it waited for `perform()`), waited out `STARTING` (self-stop deadlock), overflowed `interval * 1000000`, and sampled overhead even after a `performNow()` wake-up (doubling the next interval). Used by marmot (`start()` / `stop(true)` only). |
| `RecurringScheduleImpl` | shared `CamusExecutor` pool | Built through `CamusExecutor.createScheduleWithFixedRate/Delay`, not constructed directly. |

Shared control surface: `getState()` (`STARTING`/`WORKING`/`IDLE`/`STOPPING`/`STOPPED`), `getFailureCause()`, `getInterval()`/`setInterval(millis)` (live-updatable), `performNow()` (requests an immediate iteration of an IDLE schedule; returns whether the request was accepted — `RecurringScheduleImpl` throws `UnsupportedOperationException`), `start()`, `stop(mayInterruptIfRunning)`, `waitForStopped()`/`waitForStopped(timeout)`.

`stop()` returns before `onStopped()` necessarily ran — chain `waitForStopped()` when cleanup must be complete. Calling `waitForStopped()` from inside `perform()` on your own schedule throws `RuntimeException` (deadlock guard).

## Executors

- **`CamusExecutor`** (impl `CamusExecutorImpl`) — `Executor` plus `submit(Runnable|Callable)`, `schedule(task, delay[, unit])`, `createScheduleWithFixedRate/Delay(...)`, `stop(shutdownBaseExecutor)`. Wraps an injected `ExecutorService` or creates its own.
- **`ExecutorAware`** — `getExecutor`/`setExecutor`; the container injects after property setup and before `Initializable.initialize()`.
- **`AsyncConsumer<T> implements Consumer<T>`** — pushes consumption onto a pool. `singleWorker(consumer[, executor])`, `multipleWorkers(statelessConsumer, nThreads)`, `from(statelessConsumer, executor)`. `accept()` is fire-and-forget; `schedule()` returns a `CompletableFuture<Void>`. The multi-worker factories require a **stateless** consumer.
- **`SingleWaiterExecutor`** — at most one running `StartableExecution` plus a single pending slot. A new `submit` while one is running `cancel(true)`s whatever was pending and takes its place (latest-wins). Not an `Executor`; fire-and-forget, so track completion via the execution's own finish callbacks.
- **`CallerRunsSerialExecutor`** — `Executor` that runs tasks one at a time in FIFO order **without its own thread**: whichever thread enqueues while no one is draining becomes the dispatcher and drains the queue, including tasks other threads add meanwhile. `execute` (fire-and-forget, failures only logged), `submit(Callable)` / `submit(Runnable)` (→ `CompletableFuture`), `invokeOrDefer` (waits, unless waiting would deadlock — the caller is the dispatcher, or holds the optional `outerLock` while another thread drains — in which case it only enqueues; returns an `Invocation`: `isDeferred()`, `completion()`, and `get()` which, for a non-deferred call, rethrows the task's **original** exception — a `CompletionException` the task threw itself is not unwrapped, which is why `Task` records the failure beside the future. Deferred ≠ not run: resending runs the task twice). Cancelling a returned future does not stop the task; a task whose future is already done when it reaches the head of the queue is skipped (best-effort). `runAsDispatcher` (advanced; bypasses the queue: waits for the dispatcher role, runs the task on the caller thread, then drains what queued meanwhile; rejects a caller holding `outerLock`. **Can starve** — the dispatcher only lets go when the queue is empty, and nothing hands the role to a waiter. **Called from the dispatcher it runs inline, nested inside the current task**, ahead of everything queued). Javadoc lists the costs (dispatcher can be held long, no thread affinity, non-async future callbacks registered before completion run on the dispatcher — but callbacks registered after completion, or fired by a caller completing/cancelling the future, run elsewhere, so never assume callbacks are inside the serial order) and the differences from Guava `MoreExecutors.newSequentialExecutor(directExecutor())` — use Guava when plain fire-and-forget ordering is enough. `StateChart`'s signal queue is built on it (outer lock = the chart lock; `postSignal` returns `submit(...).copy()` so callers cancelling or timing out the future cannot drop a signal — do the same wherever a submitted task must run regardless of what the caller does with its future).
- **`Timer`** — backs `Execution.setTimeout` (`EventDrivenExecution.setTimeout` → `Executions.getTimer()`, a lazily created holder singleton that is never shut down). `setTimer(execution, timeout, unit)` / `setTimer(execution, Date)` return a `Timer.TimeoutHandle` that represents only the **schedule**: `cancel()` unschedules (never cancels the execution), `isPending()` / `isCancelled()` / `isExpired()` (expired = the `cancel(true)` request was handed to the canceller; it does not mean it ran or that the execution finished). Re-scheduling the same execution **adds** a timer; extend a deadline by cancelling the old handle first. Implementation (rewritten 2026-10-31): a 1-thread daemon `ScheduledThreadPoolExecutor` with `setRemoveOnCancelPolicy(true)` only measures time and hands expiry to a bounded daemon "canceller" pool (`MAX_CANCELLATION_THREADS` = 4, unbounded queue, idle threads time out; no `CallerRunsPolicy`, which would run cancels on the scheduler again), which calls `exec.cancel(true)` if not done (a rejected cancel is logged at DEBUG with the state — it can race a normal finish) — so a slow cancel never blocks time-keeping; past 4 blocked cancels, later ones queue and no timer lock is held while waiting for an execution's lock. `exec.whenFinished(r -> future.cancel(false))` releases the timer as soon as the execution finishes (a sync listener is fine: `cancel(false)` only removes from the queue). Monotonic time; the `Date` overload converts to a delay at registration (past dates, including `Long.MIN_VALUE`, become 0 — the plain subtraction overflowed). `shutdown()` cancels every pending handle (`shutdownNow()` only drains the queue without completing the futures); `setTimer` after `shutdown()` → `IllegalStateException`. The `whenFinished` listener the timer registers is not retained after the execution finishes (`EventDrivenExecution` clears its finish listeners after notifying and does not store listeners added after completion). Threads are named `execution-timer-N` / `execution-timer-cancel-N`. The old implementation used a `MinMaxPriorityQueue.maximumSize(64)` that silently evicted the furthest deadline, kept finished executions queued until their deadline, and called `cancel(true)` under the timer lock. Tests: `utils.async.TimerTest`.

## Inter-thread hand-off

- **`LengthOneOverridingQueue<T>`** — length-1, latest-wins: `add` overwrites an unconsumed item with no notification. `add` rejects `null` (it is the empty sentinel). `poll()` blocks; `poll(Duration)` throws `TimeoutException`; `peek()` is non-destructive and may return `null`. Use for coalescible values (sensor samples, progress); use a `BlockingQueue` when no event may be lost.
- **`CompletionFStream<T> extends SuppliableFStream<Result<T>>`** — submit executions, consume results in **completion order**. Note the element type is `Result<T>`, not `T`; failures and cancellations arrive as stream elements, not exceptions. `submit` auto-starts a `StartableExecution` and throws `IllegalStateException` after close/`endOfSupply`. Completion callbacks fill the buffer **synchronously on the worker thread**, so a full buffer blocks workers — size the buffer against the pool.
- **`CoalescingSupplier<T> implements CheckedSupplier<T>`** — call coalescing, **not memoization**. Concurrent `get()` calls share one in-flight computation (result or exception); non-overlapping calls each recompute. For real caching use `utils.func.Lazy` / `ReloadableLazy` / `TimedLazy`. API: `get()` (waits without limit; no `TimeoutException`) and `get(Duration joinTimeout)` (per call; bounds only the wait for another thread's production, never the producing call; values beyond the nanosecond range saturate to `Long.MAX_VALUE` ns). Each production gets its own `CompletableFuture` (`m_inFlightResult`, cleared by `clearInFlightIfCurrent()` under the guard **before** it is completed, so later callers start a new production): waiters get exactly the production they joined, `null` results are shared, and every caller gets the same object. A failure reaches every caller as `ExecutionException` with the same cause — including a `CancellationException` thrown by the source (`CompletableFuture.get()` would rethrow it unwrapped, so the wait path wraps it); the producer gets `InterruptedException` if it was itself interrupted; a `VirtualMachineError` is rethrown after waiters are completed. **Reentrant calls** (the source calling the same supplier) are rejected with `IllegalStateException` (`m_producerThread`), since they would wait for their own result. `getWaitingCount()` (package-private) reports blocked waiters via `getNumberOfDependents()`; tests synchronize on it instead of sleeping. History (2026-10-31): named `InterThreadShareSupplier`, with a shared `setWaitTimeout()` (removed, no alias; no users outside utils); the old code skipped the wait when no timeout was set (stale value or NPE), treated `null` as failure, and could make a waiter join the next production. Tests: `CoalescingSupplierTest`.

## Conventions

- Argument validation uses `utils.Preconditions`. `ConditionVariable` still imports Guava `Preconditions` — new code should not.
- Fields protected by a `Guard` carry `@GuardedBy("m_guard")`.
- Classes that log implement `utils.LoggerSettable` (`RecurringScheduleImpl`, `RecurringScheduleThread`, `SingleWaiterExecutor`, `CoalescingSupplier`).
- Korean Javadoc dominant; preserve language when modifying.
- Tests exist only for `Guard`, `CompletionFStream`, `CallerRunsSerialExecutor`, `CoalescingSupplier` and `RecurringScheduleThread` (`src/test/java/utils/thread/`), plus `Timer` in `utils.async.TimerTest`. Changes elsewhere in this package are unguarded by tests.

## Common gotchas

- `signalAll()` called outside the lock throws `IllegalMonitorStateException`. Work mode and `andRun`/`andGet` handle it for you.
- `andReturn()` does not signal — see above.
- `Guard.get()` signals on every read.
- `RecurringSchedule.stop()` is a request, not a join.
- `LengthOneOverridingQueue` drops events by design.
