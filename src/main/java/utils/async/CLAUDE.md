# utils.async

Async execution primitives. Built on `Execution<T> extends Future<T>` with explicit lifecycle state (`AsyncState`) and listener-based completion handling. Subpackages: [op/](op/) (combinators), [command/](command/) (sub-process orchestration). User guide for the thread-based Execution family (threaded/loop/periodic/poller) and Service family (`AbstractLoopService`/`PeriodicLoopService`): [docs/async-threaded-guide.md](../../../../../docs/async-threaded-guide.md). User guide for `command/` (`CommandExecution`, `CommandVariable`, `ProgramService`): [docs/async-command-guide.md](../../../../../docs/async-command-guide.md).

## Core types

- **`Execution<T>`** — `Future<T>` extension. Adds `AsyncState` (+ `isNotStarted`/`isRunning`/`isCompleted`/`isFailed`/`isCancelled` predicates), `whenStarted`/`whenStartedAsync`/`whenFinished`/`whenFinishedAsync` listeners, `map` chaining, `poll()`, `waitForStarted`/`waitWhileStarting`/`waitForFinished` (each with no-arg, `(timeout, TimeUnit)`, and `(Date due)` forms), `get(Date)`/`getUnchecked()`, and `setTimeout(long, TimeUnit)`. There is **no `flatMap` method on any `Execution`** — chaining is the static combinator `AsyncExecutions.flatMap(Execution<T>, Function<? super Result<T>, ? extends EventDrivenExecution<S>>)` in [op/](op/); the `EventDrivenExecution` constraint is on the *follower* it returns, not on the leader.
- **`AsyncState`** — `NOT_STARTED` → `STARTING` → `RUNNING` → terminal (`COMPLETED` | `CANCELLED` | `FAILED`). `CANCELLING` is a transition state requested via `cancel(true)`.
- **`AsyncResult<T>`** — Snapshot of a finished/running execution. Returned by `poll()` and `waitForFinished()`.
- **`Result<T>`** (in `utils.func`) — Sum type for completion outcome; used by `getResult()` and `whenFinished` callback (`ifSuccessful`/`ifFailed`/`ifNone`).
- **`Startable`**, **`StartableExecution<T>`** — Marker interfaces for executions with explicit `start()`.
- **`CancellableWork`** — Marker interface that opts in to forced cancel via `cancel(true)` (default `cancel(true)` only works on `NOT_STARTED`).
- **`Cancellable`** — Older marker (kept for backward compatibility).

## Key implementations

- **`EventDrivenExecution<T>`** — Default base. State transitions driven by `notifyStarting/Started/Completed/Failed/Cancelling/Cancelled`. **Almost every other Execution implementation extends this.**
- **`AbstractAsyncExecution<T>`** — Adds `Startable` + `ExecutorAware`. Subclass implements `start()`.
- **`AbstractThreadedExecution<T>`** — `start()` spawns a thread (or submits to injected `Executor`). Subclass implements `executeWork()` (and optionally `initializeThread()`). Provides `run()` for synchronous in-thread execution. `onResultDiscarded(T)` is called (on the worker, before `finalizeThread()`) when `executeWork()` returned a result but `notifyCompleted()` failed because the execution was already terminated externally — keyed on the actual transition failing, so it never misses a result that did not get delivered; use it to close a result that owns resources.
- **`AbstractLoopExecution<T>`** — `executeWork()` is a loop with `initializeLoop` / `iterate(long)` / `finalizeLoop` hooks. Cooperative cancel via `isCancelRequested()`. Inside `finalizeLoop()`, `getLoopOutcome()` returns how the loop ended (completed/failed+cause/cancelled, or the externally settled result) — `poll()` cannot, since the terminal transition happens after `finalizeLoop()`.
- **`PeriodicLoopExecution<T>`** — `AbstractLoopExecution` with a fixed inter-iteration interval. Constructor takes an `IntervalMode`: `FIXED_RATE` (loop-start-relative due, with catch-up if an iteration overruns the interval) or `FIXED_DELAY` (delay measured from end of the previous iteration; the default for the single-arg constructor). `IntervalMode.fromCumulative(boolean)` converts a legacy `cumulativeInterval` flag. `getIntervalMode()` reports the mode. The interval is final after construction. Supports `setTimeout(Duration)` / `setDue(Instant)` for hard loop deadlines; `getRemainingTime()` reports the time left (`empty` before start or with no deadline).
- **`AbstractPeriodicPoller<R>`** — Specialization of `PeriodicLoopExecution` for "poll until target state observed". Subclass implements `tryPoll()` (returns `FOption<R>`: present = done, empty = continue). Hooks, in call order: `initializePoller()` → `tryPoll()` (repeated) → `onTargetReached(R)` (once, when the target is reached; returns the final result, and **its exceptions fail/cancel the poller** — put result-applying work here) → `onTargetDiscarded(R)` (at most once per value, only if a reached value was *not* delivered as the result: external termination before/during `onTargetReached`, `onTargetReached` threw, or termination landed after adoption — the last case is detected both at cleanup time and, via `onResultDiscarded`, when the completion transition itself fails, so termination during or after `cleanupPoller` is covered too; ownership is cleared on the first discard so it never fires twice. Close resources the value owns here; exceptions only logged) → `cleanupPoller(AsyncResult<R>)` (always once after a successful `initializePoller`; receives the outcome — completed with value (possibly `null`), failed with cause (`TimeoutException` on timeout), or cancelled; **exceptions only logged**). `tryPoll`/`onTargetReached` may throw any `Exception`: `InterruptedException`/`CancellationException` cancel, anything else fails with that exception as the cause (no need to wrap in `ExecutionException`). The outcome comes from `AbstractLoopExecution.getLoopOutcome()`, because at cleanup time the execution is still `RUNNING` and `poll()` has no result yet; termination landing in the gap between cleanup and the terminal transition can still make it differ from the final state. (The old `finalizePoller(@Nullable R)` hook was removed: it could not tell a failure from a completed `null` result.) If the execution is already terminal, `onTargetReached` is skipped and its value goes to `onTargetDiscarded`; a terminal state reached *during* `onTargetReached` means its return value is not adopted. `onTargetReached`'s side effects are not rolled back, so callers must check for `COMPLETED` before trusting state it applied. `CANCELLING` is not terminal: a target reached while cancelling still runs `onTargetReached` and may complete. The single-arg constructor uses **`IntervalMode.FIXED_DELAY`** — a slow poll is still followed by a full interval, so a slow remote server or a reconnect target is never hammered back-to-back; pass `IntervalMode.FIXED_RATE` for catch-up. `getPollAttempt()` gives the 0-based index of the current poll inside `tryPoll`/`onTargetReached` (the last one inside cleanup; `-1` before the first poll) — use it instead of keeping a counter. `getRemainingTime()` (from `PeriodicLoopExecution`) gives the time left until the deadline — pass it as the per-request timeout of remote calls, since the loop deadline never interrupts an in-flight call.
- **`PeriodicPoller<T>`** — Concrete builder-based variant of `AbstractPeriodicPoller`. Static factories: `poll(CheckedSupplier)` (non-null = done), `poll(CheckedFunction<PollContext,T>)` (same, but the function gets `PollContext` — `attempt()` (0-based) and `remainingTime()`, e.g. to pass as the per-request timeout of a remote call; overload is resolved by lambda arity), `pollUntil(CheckedSupplier<Boolean>)`, `pollWhile(CheckedSupplier<Boolean>)` (both always yield `Boolean.TRUE` — the value is meaningless, even for `pollWhile` which ends when the condition turns **false**; judge by the execution reaching `COMPLETED`). Builder configures `fixedRate` (`FIXED_RATE`) / `fixedDelay` (`FIXED_DELAY`) — mutually exclusive, last call wins; neither set = `fixedDelay(1s)` — plus `timeout`/`due` (due wins if both set; `timeout` is measured from when polling actually starts, not from builder creation; a past `due` fails at start before `initializer`/supplier/`cleanup` run), `initializer`, `onDiscarded(CheckedConsumer<T>)` (closes a value the supplier returned that was not adopted as the result — **set it whenever the supplier returns a resource such as a connection**), `cleanup(CheckedConsumer<AsyncResult<T>>)` (the `cleanupPoller` outcome), and `name`. Supplier exceptions propagate unwrapped as the failure cause.
- **`AbstractLoopService`** — Guava `AbstractExecutionThreadService` plus a stop-request flag: `isStopRequested()` is a lock-free `volatile` read (cheap to poll inside long work), `markStopRequested()` sets it under `m_guard` and wakes waiters, `awaitUntilStopRequested()` blocks on it. `markStopRequested()` does not change the Guava state by itself — calling it directly ends the loop and the service goes `TERMINATED` without `stopAsync()`. The flag is never reset (services cannot restart).
- **`PeriodicLoopService`** — Concrete builder-based Guava `AbstractExecutionThreadService` that repeats a task on a fixed period. Subclasses overriding `performPeriodicAction(long)` can call `super(name, interval, IntervalMode)` (defaults for everything else; override `startUp()`/`shutDown()` for init/cleanup) or `super(builder)` when they need builder settings. Builder: `task(CheckedRunnable)` or `task(CheckedConsumer<LoopContext>)` / `builder(ctx -> ...)` — `LoopContext` gives `iteration()` and a lock-free `isStopRequested()` so a lambda task can bail out on `stopAsync()` (overloads resolve by lambda arity) — or override `performPeriodicAction(long)`, `fixedRate` (`IntervalMode.FIXED_RATE`, catch-up; the default, 1s) vs `fixedDelay` (`FIXED_DELAY`, measured from iteration end) — mutually exclusive, last call wins — plus `initialDelay`, `errorPolicy(ErrorPolicy)` — `STOP` (default: first failure fails the service), `CONTINUE`, or `failAfterConsecutiveFailures(n)` (fails the service on the n-th failure *in a row*; a success resets the streak); `stopOnError(boolean)` is an alias for `STOP`/`CONTINUE`. `build()` rejects a builder with no task (subclasses pass the builder to `super(builder)` instead). While a streak continues, it logs one stack-trace WARN, then DEBUG plus a reminder WARN at 10/100/1000… failures, and an INFO on recovery — `getConsecutiveFailureCount()` exposes the streak. `initializer`/`cleanup` (named to match `PeriodicPoller.Builder`), `name`, `daemon` (loop thread is a **daemon** thread by default — unlike Guava's default — so a service never stopped does not keep the JVM alive; use `daemon(false)` when the service must keep the process running). Scheduling (period and `initialDelay`) uses the monotonic clock (`System.nanoTime()` + `Guard.awaitCondition(..., Duration)`), so wall-clock jumps neither burst nor stall the loop. `stopAsync()` → `triggerShutdown()` → `markStopRequested()` wakes the sleeping loop; an in-flight iteration still runs to completion. Interrupts are treated as a graceful stop (TERMINATED, not FAILED), and the interrupt flag is checked directly before every iteration (a `FIXED_RATE` catch-up never waits, so the wait alone would miss it); `cleanup` runs with the flag cleared and restored afterwards so its blocking calls are not cut short — including a task that throws `RuntimeInterruptedException` or any exception while the loop thread's interrupt flag is set; an `InterruptedException` merely somewhere in the cause chain (e.g. another thread's task) is still a failure.
- **`CompletableFutureAsyncExecution<T>`** — Bridges `CompletableFuture<T>` into `Execution<T>`. Implements `CancellableWork`.
- **`ListenableFutureAsyncExecution<T>`** — Bridges a Guava `ListenableFuture<T>` into `Execution<T>`. Subclass implements `startExecution()` to launch and return the future; a `FutureCallback` drives `notifyCompleted`/`notifyFailed`, mapping an unwrapped `CancellationException` to `notifyCancelled`. Implements `StartableExecution` + `CancellableWork` (`cancelWork()` → `future.cancel(true)`).

## Cancellation flow

1. External thread calls `cancel(true)`.
2. `notifyCancelling()` transitions `RUNNING → CANCELLING` (or returns immediately if already past RUNNING).
3. If the execution implements `CancellableWork`, `cancelWork()` is called *outside* the lock.
4. `cancel(true)` returns `true`. **Terminal state transition is NOT awaited** — it happens asynchronously when the worker thread exits its loop and calls `notifyCancelled` / `notifyFailed` / `notifyCompleted`.
5. Use `waitForFinished()` to await the terminal state.

`cancel(false)` only works on `NOT_STARTED` (or when `CancellableWork`). For RUNNING + non-`CancellableWork` non-interruptible, returns `false`.

`checkCancelled()` and `isCancelRequested()` on `EventDrivenExecution` are the cooperative-cancel helpers used inside loop bodies.

## Concurrency primitives

- **`AsyncUtils`**, **`Executions`** — Static factories and helpers (e.g. `Executions.getTimer()` exposes the shared timer used by `setTimeout`).

Generic concurrency primitives previously living here have moved to `utils.thread`:

- **`utils.thread.Guard`** — `ReentrantLock` + `Condition` wrapper. The `m_aopGuard` field on `EventDrivenExecution` (protected, reentrant) is the canonical state-protection lock. `awaitCondition(predicate).andReturn()` / `.andRunChecked(task)` is the standard wait pattern.
- **`utils.thread.Timer`** — Schedules timeouts on `Execution` via `setTimeout`.
- **`utils.thread.SingleWaiterExecutor`** — Latest-wins single-slot executor (one running + one pending; new submit replaces and cancels pending).
- **`utils.thread.LengthOneOverridingQueue`** — Single-slot blocking queue where new offers overwrite the pending element.
- **`utils.thread.AsyncConsumer`** — Async consumer helper.

## Subpackages

- **[utils.async.op](op/)** — Combinators (`SequentialAsyncExecution`, `ConcurrentAsyncExecution`, `FoldedAsyncExecution`, `TimedAsyncExecution`, `BackgroundedAsyncExecution`, `DelayedAsyncExecution`, `FlatMapAsyncExecution`) + `AsyncExecutions` static factory façade.
- **[utils.async.command](command/)** — Sub-process orchestration:
  - `CommandExecution` — builder-based; variable substitution, stdin/stdout/stderr redirection, timeout, SIGTERM-then-SIGKILL termination via `utils.ProcessTree`. Streams are configured with value objects: `stdin(Input)` — `Input.none()` (default, OS null device: EOF on read), `Input.inherit()`, `Input.file(f)`; `stdout(Output)` / `stderr(Output)` — `Output.discard()` (default), `Output.inherit()`, `Output.file(f)` (overwrite) / `Output.file(f).append()`, and `Output.toStdout()` (stderr only; merges into stdout, rejected by `stdout()`). Both are sealed interfaces nested in `CommandExecution` (records/enum singletons), relative files resolve against the working directory at run time, and re-setting a stream replaces it. The old per-stream methods (`redirectStdoutToFile`, `discardStdin`, `redirectErrorStream`, …) were removed — callers in MDT were migrated. `Input.none()` is the default because the `Process` is never exposed, so a `PIPE` default would only hang a child that reads stdin. An exit code outside `successExitCodes(int...)` (default `{0}`; replaces, does not accumulate — e.g. `successExitCodes(0, 1)` for `grep`) fails with `CommandFailedException` (an `ExecutionException`; message `Process failed: retCode=N`) carrying `getExitCode()` and `getOutputTail()` — the last ≤4KB of the stderr file, or the stdout file when stderr is not in its own file; `null` when output is not in a file. `getExitCode()` (`OptionalInt`) reports the actual code after the process exits, success or failure — empty before exit or when timeout/cancel ended it first. `cancel(true)` does not wait: `cancelWork()` hands `ProcessTree.terminate(grace)` to `Executions.getExecutor()`, and `executeWork()`'s `finally` reaps stragglers — **before** the terminal transition, so a finish listener on the `CommandExecution` itself runs after cleanup (a wrapper around it, e.g. `AsyncExecutions.delay`, may finish earlier). If the state is settled externally while `initializeThread()` is still running (e.g. `notifyFailed()`), `executeWork()` never runs; `abortAfterInitialize()` terminates the process instead. `close()` separates "terminal" from "cleaned up": it marks the execution closed (a worker that has not created the process yet will not), terminates any process still held, and waits on `m_workerActive` until the worker has released it. **Descendant cleanup is best-effort**: descendants are found by polling `ProcessHandle` parent links, so a child whose parent forks and exits between polls (daemonizing programs) escapes — documented in the class Javadoc; reliable cleanup would need OS process groups / job objects. `getVariableMap()` is read-only. Logging never includes the variable-substituted command line (values may be secrets): INFO has the program and working directory, DEBUG the command line *before* substitution — a secret written literally into the command line still shows at DEBUG. `executeWork()` is `protected`.
  - `CommandVariable` — created through role factories (the public constructors were removed; subclasses such as MDT's `MDTCommandVariable` use the `protected (name, value, file, deleteOnClose)` constructor): `input(name, value)` (temp file on `path`, deleted on close), `input(name, value, file)` (value **overwrites** the file on `path` — the old constructor silently kept an existing file's content instead; file deleted on close; also usable as an in/out variable), `inputFile(name, file)` (caller-owned, **never deleted** — the old constructor deleted any file on close, including a user's own), `inputFile(name, file, true)` (a copy made for the run, deleted on close), `output(name, file)` (deletes a stale file at creation so a run that writes nothing cannot return the previous run's result; deleted on close). Named value held inline or in a file; referenced from the command line as `${<var>:<modifier>}` where the modifier is `name` (default), `value`, or `path` (`path` materializes the value into a file and substitutes its absolute path; a value-only `CommandVariable(name, value)` gets a temp file `cmdvar-*.txt`, owner-only on POSIX, on the first `path` request — `getFile()` is `null` until then). In file mode `getValue()` re-reads the file on every call (no first-read cache), so reading an output variable early does not pin a stale value. `CommandVariable` is `AutoCloseable`; a `path` request after `close()` throws `IllegalStateException` (a closed variable re-creating a file would leak it), while `getValue()`/`name` keep working. `close()` reads the file once more and then deletes it; afterwards `getValue()` returns that last read value (`IllegalStateException` if the file could never be read). Reading on close is required: `RESTfulAsyncRpcServer` closes the execution as soon as it finishes and collects outputs later.
  - `ProgramService` — supervises a child process on the Guava `AbstractService` lifecycle, restarting it per `RestartPolicy` (default `ALWAYS`) with `restartDelay`. The policy applies only after the service is `RUNNING`: if the *first* execution ends before reaching `RUNNING` (missing executable, unreadable env file…) the service goes `FAILED` regardless of policy; if it does not reach `RUNNING` within `startTimeout` (default 30s, `"0s"` = no limit) the service goes `FAILED` with a `TimeoutException` and the execution is cancelled (a late `RUNNING` is cancelled too — `m_startSettled` lets exactly one of start/finish/timeout move the service). `stopAsync()` during `STARTING` cancels the pending execution via `doCancelStart()`. If building or starting the next execution for a restart throws (e.g. the working directory vanished) the service goes `FAILED` instead of staying `RUNNING` with no child. The service keeps a **copy** of its config (`new ProgramServiceConfig(config)`, command line and environment made unmodifiable; an empty command line is rejected at `create`), so mutating the caller's config object never changes later restarts. `create(File)` parses the JSON first and substitutes `${env:…}`/`${sys:…}` only inside string values (object keys untouched) — substituting the raw text broke JSON on values with quotes/backslashes/newlines; references must therefore sit inside strings (`"restartLimit": "${env:N}"` still binds via Jackson coercion). Finish handling is registered with `whenFinishedAsync` on the **`CommandExecution`** (not on the delay wrapper), so it runs outside the execution's lock and only after the process is cleaned up; a delay wrapper that fails before starting its target is routed to the same handler (an `AtomicBoolean` guarantees one call). `doStop()` and `doCancelStart()` send `cancel(true)` from another thread: `cancel()` takes the execution's lock, and doing that while holding Guava's monitor deadlocked against a finish listener that held the execution's lock and called `notifyStopped()`. The first execution's `whenStarted` → `notifyStarted()` stays synchronous (making it async could let a fast-exiting first run's finish handler overtake it); it is safe because nothing holds Guava's monitor while waiting for the execution's lock. `doStop()` never waits — when an execution finishes, the restart handling decides the next action (`decide()`, no Guava calls), commits it under `m_guard` (a stop requested meanwhile wins: no next execution, `notifyStopped()`), then applies it outside the guard, so a `stopAsync()` racing a restart cannot deadlock against `notifyStopped()`/`notifyFailed()`. **Restart backoff** (on by default): each run shorter than `stableRunTime` (10s) counts as short; from the second short run in a row the delay doubles from `max(restartDelay, 1s)` up to `maxRestartDelay` (1m) — `computeRestartDelay(base, max, shortRuns)` is the package-private pure function — and one run of at least `stableRunTime` resets it; `maxRestartDelay <= restartDelay` disables backoff (tests that want fast restarts set `maxRestartDelay` to `ZERO`). This keeps a crash-on-start program from spinning (CPU, and the appended `application.log`). **Restart limit** (off by default, `restartLimit = 0`): with `restartLimit = N`, an (N+1)-th restart inside a sliding `restartLimitInterval` (1m) fails the service with `IllegalStateException("restart limit exceeded: …")`, so a crash loop shows up as `FAILED` instead of a perpetual `RUNNING`. Backoff/limit state (`m_consecutiveShortRuns`, `m_restartNanos`) is touched only from the sequential finish callbacks; run time is measured from the child's `whenStarted`. Child stdout/stderr are merged and **appended** to `application.log` in the working directory (a restart keeps the previous run's output; nothing rotates it). `getRestartCount()` counts restarts (not the first run; a restart waiting out its delay counts) and `getLastExitCode()` (`OptionalInt`) keeps the exit code of the latest run that exited by itself — runs ended by stop/cancel without a code do not overwrite it — for diagnosing a crash loop. Package-private `setExecutor(Executor)` exists for tests that need to hold an execution in `STARTING`.
  - `ProgramServiceConfig` — JSON-loadable config: command line, working directory, environment, restart policy, `restartDelay`, `maxRestartDelay`, `stableRunTime`, `restartLimit`, `restartLimitInterval`, `startTimeout` (a `Duration` in the Java API like the others; `DEFAULT_START_TIMEOUT` is `Duration.ofSeconds(30)`). Copy constructor `ProgramServiceConfig(ProgramServiceConfig)`. Duration fields accept `UnitUtils.parseDuration` strings (`"5s"`, `"1m"`, `"PT5S"`) in JSON and serialize as ISO-8601.
  - `RestartPolicy` — `fromString` is the Jackson `@JsonCreator` and accepts both constant names (`"ON_COMPLETED"`) and kebab names (`"on-completed"`), case-insensitive; serialization and `toString()` use the constant name.
  - `ServiceShutdownHook` — JVM shutdown hook for Guava `Service`s; waits `DEFAULT_TERMINATION_TIMEOUT` (3s) for `TERMINATED`, or the timeout given to `register(name, service, Duration)`; unregister via the returned `Registration` on the normal path.

## Downstream

- **`utils.rpc.restful`** — Exposes an `Execution` as a remote operation over HTTP. `RESTfulAsyncRpcServer` starts a `StartableExecution` per request and serves status/cancel against it; `RESTfulAsyncRpcClient` is an `AbstractPeriodicPoller` that polls the resulting session to completion. `utils.rpc.restful.process` wires `CommandExecution` into that server.

## Conventions

- Subclasses access state via `m_aopGuard` (protected on `EventDrivenExecution`). State transitions are serialized through this lock; `getInAsyncExecutionGuard(Supplier)` / `runInAsyncExecutionGuard(Runnable)` for external state-coupled operations.
- `whenStarted` listeners fire only when the execution actually reached RUNNING. `NOT_STARTED → CANCELLED` (cancel before start) skips them.
- `whenFinished` always fires on terminal transition.
- `Async`-suffixed variants run the listener via `CompletableFuture.runAsync`. Non-async variants run synchronously inside the lock.
- Argument validation uses `utils.Preconditions.checkNotNullArgument` / `checkArgument`. Avoid Guava `Preconditions` in new code.
- Korean Javadoc dominant; preserve language when modifying.

## Common gotchas

- `notifyStarting` is **idempotent** for STARTING (returns `true` even if already STARTING). Don't rely on it as a "first call wins" guard for parallel `start()`.
- `notifyCompleted`/`notifyFailed`/`notifyCancelled` accept `RUNNING` and `CANCELLING` (so a cancel-in-progress can still be completed/failed). They reject `NOT_STARTED`/`STARTING` for `notifyCompleted`.
- `notifyCancelling` and `notifyCancelled` wait while state is `STARTING` (with `cancelTimeout`, default 3s) — calling them from within the same thread that holds STARTING leads to deadlock-like timeout.
- **`CommandExecution` fails on an unresolved `${X}`.** Command-line substitution runs in two passes — general variables (`${WORKING_DIR}`, `${env:…}`) then `CommandVariable`s — and the *second* pass throws `IllegalArgumentException` ("Cannot resolve variable") for anything still unmatched, so the sub-process never starts and the execution goes to FAILED. A substituted `CommandVariable` *value* is never re-substituted (`setDisableSubstitutionInValues(true)`): a `${…}` inside a value reaches the sub-process literally instead of leaking another variable's value or failing as undefined. The unresolved-`${X}` failure is deliberate: letting a typo'd variable name through to the shell as a literal token fails silently and much later. Note the failure surfaces oddly if the caller ignores the result — `waitForFinished()` does not rethrow, so the next line (e.g. reading the redirected stdout file) blows up with an unrelated `NoSuchFileException`. Check `AsyncResult.getFailureCause()`.
- `AbstractLoopExecution` does NOT implement `CancellableWork` — cooperative-cancel via `isCancelRequested()` is the mechanism. Worker exits its loop when it sees the cancel request at the next iteration boundary, or when the execution is already terminal (e.g. a subclass's `cancelWork()` threw and `cancel()` moved it to `FAILED`, or someone called `notifyFailed()` from outside) — the settled state is kept and `finalizeLoop()` still runs. `PeriodicLoopExecution`'s inter-iteration wait wakes on either condition too.
