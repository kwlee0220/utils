# utils.async

Async execution primitives. Built on `Execution<T> extends Future<T>` with explicit lifecycle state (`AsyncState`) and listener-based completion handling. Subpackages: [op/](op/) (combinators), [command/](command/) (sub-process orchestration). User guide for the threaded/loop/periodic/poller family: [docs/async-execution-guide.md](../../../../../docs/async-execution-guide.md).

## Core types

- **`Execution<T>`** — `Future<T>` extension. Adds `AsyncState` (+ `isNotStarted`/`isRunning`/`isCompleted`/`isFailed`/`isCancelled` predicates), `whenStarted`/`whenStartedAsync`/`whenFinished`/`whenFinishedAsync` listeners, `map` chaining, `poll()`, `waitForStarted`/`waitWhileStarting`/`waitForFinished` (each with no-arg, `(timeout, TimeUnit)`, and `(Date due)` forms), `get(Date)`/`getUnchecked()`, and `setTimeout(long, TimeUnit)`. There is **no `flatMap` method on any `Execution`** — chaining is the static combinator `AsyncExecutions.flatMap(Execution<T>, Function<? super Result<T>, ? extends EventDrivenExecution<S>>)` in [op/](op/); the `EventDrivenExecution` constraint is on the *follower* it returns, not on the leader.
- **`AsyncState`** — `NOT_STARTED` → `STARTING` → `RUNNING` → terminal (`COMPLETED` | `CANCELLED` | `FAILED`). `CANCELLING` is a transition state requested via `cancel(true)`.
- **`AsyncResult<T>`** — Snapshot of a finished/running execution. Returned by `poll()` and `waitForFinished()`.
- **`Result<T>`** (in `utils.func`) — Sum type for completion outcome; used by `getResult()` and `whenFinished` callback (`ifSuccessful`/`ifFailed`/`ifNone`).
- **`Startable`**, **`StartableExecution<T>`** — Marker interfaces for executions with explicit `start()`.
- **`CancellableWork`** — Marker interface that opts in to forced cancel via `cancel(true)` (default `cancel(true)` only works on `NOT_STARTED`).
- **`Cancellable`** — Older marker (kept for backward compatibility).

## Key implementations

- **`EventDrivenExecution<T>`** — Default base. State transitions driven by `notifyStarting/Started/Completed/Failed/Cancelling/Cancelled`. **Almost every other Execution implementation extends this.**
- **`AbstractAsyncExecution<T>`** — Adds `Startable` + `ExecutorAware`. Subclass implements `start()`.
- **`AbstractThreadedExecution<T>`** — `start()` spawns a thread (or submits to injected `Executor`). Subclass implements `executeWork()` (and optionally `initializeThread()`). Provides `run()` for synchronous in-thread execution. `onResultDiscarded(T)` is called (on the worker, before `finalizeThread()`) when `executeWork()` returned a result but `notifyCompleted()` failed because the execution was already terminated externally — keyed on the actual transition failing, so it never misses a result that did not get delivered; use it to close a result that owns resources.
- **`AbstractLoopExecution<T>`** — `executeWork()` is a loop with `initializeLoop` / `iterate(long)` / `finalizeLoop` hooks. Cooperative cancel via `isCancelRequested()`. Inside `finalizeLoop()`, `getLoopOutcome()` returns how the loop ended (completed/failed+cause/cancelled, or the externally settled result) — `poll()` cannot, since the terminal transition happens after `finalizeLoop()`.
- **`PeriodicLoopExecution<T>`** — `AbstractLoopExecution` with a fixed inter-iteration interval. Constructor takes an `IntervalMode`: `FIXED_RATE` (loop-start-relative due, with catch-up if an iteration overruns the interval) or `FIXED_DELAY` (delay measured from end of the previous iteration; the default for the single-arg constructor). The old `(Duration, boolean cumulativeInterval)` constructor is `@Deprecated` (`IntervalMode.fromCumulative(boolean)` maps it). `getIntervalMode()` reports the mode. The interval is final after construction. Supports `setTimeout(Duration)` / `setDue(Instant)` for hard loop deadlines; `getRemainingTime()` reports the time left (`empty` before start or with no deadline).
- **`AbstractPeriodicPoller<R>`** — Specialization of `PeriodicLoopExecution` for "poll until target state observed". Subclass implements `tryPoll()` (returns `FOption<R>`: present = done, empty = continue). Hooks, in call order: `initializePoller()` → `tryPoll()` (repeated) → `onTargetReached(R)` (once, when the target is reached; returns the final result, and **its exceptions fail/cancel the poller** — put result-applying work here) → `onTargetDiscarded(R)` (at most once per value, only if a reached value was *not* delivered as the result: external termination before/during `onTargetReached`, `onTargetReached` threw, or termination landed after adoption — the last case is detected both at cleanup time and, via `onResultDiscarded`, when the completion transition itself fails, so termination during or after `cleanupPoller` is covered too; ownership is cleared on the first discard so it never fires twice. Close resources the value owns here; exceptions only logged) → `cleanupPoller(AsyncResult<R>)` (always once after a successful `initializePoller`; receives the outcome — completed with value (possibly `null`), failed with cause (`TimeoutException` on timeout), or cancelled; **exceptions only logged**). `tryPoll`/`onTargetReached` may throw any `Exception`: `InterruptedException`/`CancellationException` cancel, anything else fails with that exception as the cause (no need to wrap in `ExecutionException`). The outcome comes from `AbstractLoopExecution.getLoopOutcome()`, because at cleanup time the execution is still `RUNNING` and `poll()` has no result yet; termination landing in the gap between cleanup and the terminal transition can still make it differ from the final state. The old `finalizePoller(@Nullable R)` is `@Deprecated` and still called by the default `cleanupPoller`. (The hook is deliberately *not* an overload named `finalizePoller(FOption<R>)` — that clashed by erasure with `finalizePoller(R)` when `R` is itself an `FOption`.) If the execution is already terminal, `onTargetReached` is skipped and its value goes to `onTargetDiscarded`; a terminal state reached *during* `onTargetReached` means its return value is not adopted. `onTargetReached`'s side effects are not rolled back, so callers must check for `COMPLETED` before trusting state it applied. `CANCELLING` is not terminal: a target reached while cancelling still runs `onTargetReached` and may complete. The single-arg constructor uses **`IntervalMode.FIXED_DELAY`** — a slow poll is still followed by a full interval, so a slow remote server or a reconnect target is never hammered back-to-back; pass `IntervalMode.FIXED_RATE` for catch-up (the `boolean` constructor is `@Deprecated`). `getPollAttempt()` gives the 0-based index of the current poll inside `tryPoll`/`onTargetReached` (the last one inside cleanup; `-1` before the first poll) — use it instead of keeping a counter. `getRemainingTime()` (from `PeriodicLoopExecution`) gives the time left until the deadline — pass it as the per-request timeout of remote calls, since the loop deadline never interrupts an in-flight call.
- **`PeriodicPoller<T>`** — Concrete builder-based variant of `AbstractPeriodicPoller`. Static factories: `poll(CheckedSupplier)` (non-null = done), `poll(CheckedFunction<PollContext,T>)` (same, but the function gets `PollContext` — `attempt()` (0-based) and `remainingTime()`, e.g. to pass as the per-request timeout of a remote call; overload is resolved by lambda arity), `pollUntil(CheckedSupplier<Boolean>)`, `pollWhile(CheckedSupplier<Boolean>)` (both always yield `Boolean.TRUE` — the value is meaningless, even for `pollWhile` which ends when the condition turns **false**; judge by the execution reaching `COMPLETED`). Builder configures `fixedRate` (`FIXED_RATE`) / `fixedDelay` (`FIXED_DELAY`) — mutually exclusive, last call wins; neither set = `fixedDelay(1s)`; the old `interval`/`delay` are `@Deprecated` aliases — plus `timeout`/`due` (due wins if both set; `timeout` is measured from when polling actually starts, not from builder creation; a past `due` fails at start before `initializer`/supplier/`cleanup` run), `initializer`, `onDiscarded(CheckedConsumer<T>)` (closes a value the supplier returned that was not adopted as the result — **set it whenever the supplier returns a resource such as a connection**), `cleanup(CheckedConsumer<AsyncResult<T>>)` (the `cleanupPoller` outcome), and `name`. Supplier exceptions propagate unwrapped as the failure cause.
- **`AbstractLoopService`** — Long-running service variant (start/stop loop on demand).
- **`PeriodicLoopService`** — Concrete builder-based Guava `AbstractExecutionThreadService` that repeats a task on a fixed period. Builder: `task` (or override `performPeriodicAction(long)`), `fixedRate` (`IntervalMode.FIXED_RATE`, catch-up; the default, 1s) vs `fixedDelay` (`FIXED_DELAY`, measured from iteration end) — mutually exclusive, last call wins; the old `interval`/`delay` (and `isCumulativeInterval()`, now `getIntervalMode()`) are `@Deprecated` — plus `initialDelay`, `stopOnError` (default `true` → task exception fails the service), `initializer`/`finalizer`, `name`. Scheduling (period and `initialDelay`) uses the monotonic clock (`System.nanoTime()` + `Guard.awaitCondition(..., Duration)`), so wall-clock jumps neither burst nor stall the loop. `stopAsync()` → `triggerShutdown()` → `markStopRequested()` wakes the sleeping loop; an in-flight iteration still runs to completion. Interrupts are treated as a graceful stop (TERMINATED, not FAILED).
- **`CompletableFutureAsyncExecution<T>`** — Bridges `CompletableFuture<T>` into `Execution<T>`. Implements `CancellableWork`.
- **`ListenableFutureAsyncExecution<T>`** — Bridges a Guava `ListenableFuture<T>` into `Execution<T>`. Subclass implements `startExecution()` to launch and return the future; a `FutureCallback` drives `notifyCompleted`/`notifyFailed`, mapping an unwrapped `CancellationException` to `notifyCancelled`. Implements `StartableExecution` + `CancellableWork` (`cancelWork()` → `future.cancel(true)`).

## Cancellation flow

1. External thread calls `cancel(true)`.
2. `notifyCancelling()` transitions `RUNNING → CANCELLING` (or returns immediately if already past RUNNING).
3. If the execution implements `CancellableWork`, `cancelWork()` is called *outside* the lock.
4. `cancel(true)` returns `true`. **Terminal state transition is NOT awaited** — it happens asynchronously when the worker thread exits its loop and calls `notifyCancelled` / `notifyFailed` / `notifyCompleted`.
5. Use `waitForFinished()` to await the terminal state.

`cancel(false)` only works on `NOT_STARTED` (or when `CancellableWork`). For RUNNING + non-`CancellableWork` non-interruptible, returns `false`.

`checkCancelled()` and `isCancelRequested()` on `EventDrivenExecution` are the cooperative-cancel helpers used inside loop bodies.

## Concurrency primitives

- **`FStreamExecutor`** — Bridges `utils.stream.FStream` into async execution.
- **`AsyncUtils`**, **`Executions`** — Static factories and helpers (e.g. `Executions.getTimer()` exposes the shared timer used by `setTimeout`).

Generic concurrency primitives previously living here have moved to `utils.thread`:

- **`utils.thread.Guard`** — `ReentrantLock` + `Condition` wrapper. The `m_aopGuard` field on `EventDrivenExecution` (protected, reentrant) is the canonical state-protection lock. `awaitCondition(predicate).andReturn()` / `.andRunChecked(task)` is the standard wait pattern.
- **`utils.thread.Timer`** — Schedules timeouts on `Execution` via `setTimeout`.
- **`utils.thread.SingleWaiterExecutor`** — Latest-wins single-slot executor (one running + one pending; new submit replaces and cancels pending).
- **`utils.thread.LengthOneOverridingQueue`** — Single-slot blocking queue where new offers overwrite the pending element.
- **`utils.thread.AsyncConsumer`** — Async consumer helper.

## Subpackages

- **[utils.async.op](op/)** — Combinators (`SequentialAsyncExecution`, `ConcurrentAsyncExecution`, `FoldedAsyncExecution`, `TimedAsyncExecution`, `BackgroundedAsyncExecution`, `DelayedAsyncExecution`, `FlatMapAsyncExecution`) + `AsyncExecutions` static factory façade.
- **[utils.async.command](command/)** — Sub-process orchestration: `CommandExecution` (builder-based, variable substitution, stdin/stdout/stderr redirection, timeout, SIGTERM-then-SIGKILL termination via `utils.ProcessTree`), `CommandVariable` (named value held inline or in a file; referenced from the command line as `${<var>:<modifier>}` where the modifier is `name` (default), `value`, or `path` — `path` materializes the value into a file and substitutes its absolute path), `ProgramService` (supervises a child process on the Guava `AbstractService` lifecycle, restarting it per `RestartPolicy` — default `ALWAYS` — with `restartDelay`; child stdout/stderr are merged into `application.log` in the working directory), `ProgramServiceConfig` (JSON-loadable config: command line, working directory, environment, restart policy, start timeout), `ServiceShutdownHook` (JVM shutdown hook for Guava `Service`s; unregister via the returned `Registration` on the normal path).

## Downstream

- **`utils.rpc.restful`** — Exposes an `Execution` as a remote operation over HTTP. `RESTfulAsyncRpcServer` starts a `StartableExecution` per request and serves status/cancel against it; `RESTfulAsyncRpcClient` is an `AbstractPeriodicPoller` that polls the resulting session to completion. `utils.rpc.restful.process` wires `CommandExecution` into that server.

## Conventions

- Subclasses access state via `m_aopGuard` (protected on `EventDrivenExecution`). State transitions are serialized through this lock; `getInAsyncExecutionGuard(Supplier)` / `runInAsyncExecutionGuard(Runnable)` for external state-coupled operations.
- `whenStarted` listeners fire only when the execution actually reached RUNNING. `NOT_STARTED → CANCELLED` (cancel before start) skips them.
- `whenFinished` always fires on terminal transition.
- `Async`-suffixed variants run the listener via `CompletableFuture.runAsync`. Non-async variants run synchronously inside the lock.
- Argument validation uses `utils.Preconditions.checkNotNullArgument` / `checkArgument`. Avoid Guava `Preconditions` in new code.
- Korean Javadoc dominant; preserve language when modifying.

## Common gotchas

- `notifyStarting` is **idempotent** for STARTING (returns `true` even if already STARTING). Don't rely on it as a "first call wins" guard for parallel `start()`.
- `notifyCompleted`/`notifyFailed`/`notifyCancelled` accept `RUNNING` and `CANCELLING` (so a cancel-in-progress can still be completed/failed). They reject `NOT_STARTED`/`STARTING` for `notifyCompleted`.
- `notifyCancelling` and `notifyCancelled` wait while state is `STARTING` (with `cancelTimeout`, default 3s) — calling them from within the same thread that holds STARTING leads to deadlock-like timeout.
- **`CommandExecution` fails on an unresolved `${X}`.** Command-line substitution runs in two passes — general variables (`${WORKING_DIR}`, `${env:…}`) then `CommandVariable`s — and the *second* pass throws `IllegalArgumentException` ("Cannot resolve variable") for anything still unmatched, so the sub-process never starts and the execution goes to FAILED. This is deliberate: letting a typo'd variable name through to the shell as a literal token fails silently and much later. Note the failure surfaces oddly if the caller ignores the result — `waitForFinished()` does not rethrow, so the next line (e.g. reading the redirected stdout file) blows up with an unrelated `NoSuchFileException`. Check `AsyncResult.getFailureCause()`.
- `AbstractLoopExecution` does NOT implement `CancellableWork` — cooperative-cancel via `isCancelRequested()` is the mechanism. Worker exits its loop when it sees the cancel request at the next iteration boundary, or when the execution is already terminal (e.g. a subclass's `cancelWork()` threw and `cancel()` moved it to `FAILED`, or someone called `notifyFailed()` from outside) — the settled state is kept and `finalizeLoop()` still runs. `PeriodicLoopExecution`'s inter-iteration wait wakes on either condition too.
