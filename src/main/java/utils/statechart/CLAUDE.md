# utils.statechart

Hierarchical state chart built on top of `utils.async.AbstractAsyncExecution`. State transitions are signal-driven; the chart itself is a runnable execution that completes / fails / cancels via terminal states.

## Core types

- **`StateContext<C extends StateContext<C>>`** — CRTP self-bound. Domain-specific data carrier for the chart, with back-reference to the chart. `setStateChart(this)` is called once by the `StateChart` constructor; subsequent calls must throw `IllegalStateException`.
- **`StateChart<C>`** — `extends AbstractAsyncExecution<C> implements CancellableWork`. Holds states, initial state, final-state set, and the active-state chain (`m_activeStateChain`, outermost → innermost; `m_currentState` is its last element). `getCurrentState()` returns the innermost state, `getActiveStates()` the whole chain (immutable snapshot). Driven by `handleSignal` / `processSignal` / `postSignal` (see Signal processing). Lifecycle (`start` / `complete` / `fail` / `cancel(true)`) inherited from parent.
- **`State<C>`** — Marker interface with `getPath()`, `getContext()`, `enter()`, `exit()`, `selectTransition(Signal)`. Default `enter`/`exit` are no-op.
- **`Signal`** — Empty marker for events. Application defines concrete subtypes.
- **`StateContext<C>`** — `getStateChart()` / `setStateChart(chart)` (called once by the `StateChart` constructor; a second call must throw ISE). **`AbstractStateContext<C>`** implements both (volatile field, `synchronized` set, IAE on null, ISE on second set) — extend it instead of hand-writing the contract. `WebSocketContext` still implements `StateContext` directly (it narrows the return type and checks the chart type).
- **`Transition<C>`** — `getTargetStatePath()` (Optional — empty = **internal** transition, `isInternal()`) + `execute(context, signal)` action. Not called "self-transition": in UML that means the opposite (exit + re-enter, which here is a transition whose target is the current path). Created via `Transitions.to` / `internal` / `stay` / `fail` factories — direct implementation discouraged.
- **`TransitionAction<C>`** — `BiConsumer<C, Signal>`.

## State implementations

- **`DefaultState<C>`** — concrete `AbstractState` with no-op `enter`/`exit`: `new DefaultState<>(path, ctx).on(...)` instead of an anonymous subclass.
- **`AbstractState<C>`** — Base. Stores path, context, path-segments (split by `/`, empty segments dropped so a leading `/` yields no blank head). `toString()` is `State[path]`. Owns a **`TransitionTable`** and exposes `on(signal, transition)` (equals match), `on(Type.class, transition)` (instanceof), `on(Type.class, guard, transition)` (instanceof + predicate; false = fall through), `on(Type.class, sig -> transition)` (selector; `null` = not selected, fall through), each returning `this` (`AbstractState<C>`; subclasses may override covariantly — the `StateChartTest` helpers `LogState`/`LogComposite` do). The default `selectTransition` = `table.select(signal)` (first matching entry in registration order); overriding `selectTransition` bypasses the table unless it calls `super`. `AbstractState` therefore does not force subclasses to implement `selectTransition` — a subclass that omits it compiles and simply selects nothing.
- **`AbstractTimedState<C>`** — `AbstractState` with a per-state timeout. Constructor `(path, ctx, scheduler[, signalExecutor])`; subclasses implement `getTimeout()` (positive, else ISE at arm time) and `onTimeout(Duration)`. `enter()`/`exit()` are **final** (arm → `onEnter()`, cancel → `onExit()`; an `onEnter()` exception cancels the timer, since a state whose `enter()` failed is never exited). `restartTimeout()`/`cancelTimeout()` are `protected final`; `restartTimeout()` arms only while the state is entered (`m_entered`, set in `enter()`, cleared in `exit()` and on a failed `onEnter()`), so a call from an async callback after the state was left does not re-arm a timer whose `TimedOut` would go to `onUnhandledSignal`; there is **no automatic restart on signals** (RCK has both policies: `JsonMessageState` restarts on every message, `Stopping` never). Timer and generation are **per state object** under a private lock (one per chart would let a parent and child cancel each other). Expiry posts `TimedOut(state, generation, timeout)` (public class, package-private ctor so tests can forge stale ones). **`StateChart.selectTransition` routes `TimedOut` straight to its owner** (if the owner is in the active chain → package-private `selectTimeoutTransition`: `onTimeout` if current, `stay()` if stale; otherwise empty → `onUnhandledSignal`), so no other state is asked — otherwise a child's catch-all `on(Signal.class, stay())` would swallow the parent's timeout and leave the chart running. `AbstractTimedState` therefore does not override `selectTransition`. The expiry task skips when stale or when the chart is done. Direct `complete()`/`fail()` skip `exit()`, so on its first `enter()` each state registers **one** `whenFinished(r -> leave())` on the chart (flag `m_finishHookRegistered`) that cancels the reservation; the listener only takes `m_timerLock`. `signalExecutor` (nullable) moves `postSignal` off the scheduler thread, because the signal queue runs the transition on the sending thread; if it rejects the task, the expiry is posted from the scheduler thread with a WARN (dropping it would leave a chart whose only exit is the timeout running forever). Both executors are caller-owned. Delay is `toNanos()` saturated at `Long.MAX_VALUE`. Tests: `AbstractTimedStateTest` (`ManualScheduler` records tasks and fires them on demand).
- **`TransitionTable<C>`** — The table itself, usable as a field by any `State`. `CopyOnWriteArrayList` of entries, so registering from another thread is safe (entries registered while running apply to later signals).
- **`TriggeredState<C>`** — Reacts to exactly one trigger Signal (matched via `equals`); returns a static or supplier-provided transition. A supplier returning `null` fails with `IllegalStateException` naming the state path. Other signals → `super.selectTransition` (the inherited table from `on(...)`; empty if nothing registered). `TerminalState` overrides all three `on(...)` to throw `UnsupportedOperationException` (it never selects).
- **`TerminalState<C>`** — Final-state base. `exit()` and `selectTransition` throw `UnsupportedOperationException`. **`addState` registers every `TerminalState` (incl. `FailureState`) as a final state automatically**. Explicit `addFinalState` on one is harmless.
- **`FailureState<C>`** (a "state that ends in failure", not an exception) — `extends TerminalState<C>`. Holds a `failureCause`. When chart's `executeTransition` reaches an `FailureState` that's a final state, `fail(cause)` is called instead of `complete()`. The cause must be set by the inbound transition's action before executeTransition calls `enter`.
- **`CompositeState<C>`** — `State` + `getInitialStatePath()`. Holds no runtime state: the **chart** enters/exits sub-states and walks signals up the chain.
- **`DefaultCompositeState<C>`** — `(path, context, initialStatePath)`. `enter`/`exit` no-op; no `selectTransition` override of its own — it inherits the `AbstractState` table, so "group" transitions that apply whichever sub-state is active are registered with `on(...)` (or `selectTransition` overridden).

## Transition factories (`Transitions`)

The implementation classes (`DefaultTransition`, `NoOpTransition`, `FailTransition`, `InternalTransition`, `StayTransition`) are **private** nested classes — only the factories are API.

- **`Transitions.to(targetPath, action)`** — Move to target + run action (`DefaultTransition`).
- **`Transitions.to(targetPath)`** — Move to target only (no action) (`NoOpTransition`; `toString` is `-> path`).
- **`Transitions.internal(action)`** — Internal transition: `targetStatePath` empty; the chart runs `execute` (the action) with **no** `exit`/`enter` and no final-state check. Action exceptions fail the chart like any transition failure (VME rethrown). `InternalTransition`.
- **`Transitions.fail(targetPath, signal -> cause)`** — `to(path, action)` specialised for a `FailureState` target (`FailTransition`): its action looks up the target via `context.getStateChart().findState(path)` and calls `setFailureCause(causeFunc.apply(signal))`. Throws `IllegalStateException` (→ chart fails with it, absorbed like any action failure) when the context has no chart, the target is not an `FailureState`, or `causeFunc` returns `null`. It replaces the look-up-and-cast boilerplate.
- **`Transitions.stay()`** — Internal transition with an empty action. Singleton. Still counts as "selected" (TRANSITIONED), so it stops bubbling to outer composites and `onUnhandledSignal`.

**Self-transition semantics**: empty target → `executeTransition` calls `execute` and returns, so a transition can act while staying. An explicit current-state path still does `exit` → action → `enter`.

## Hierarchy (composite states)

- **Parent is derived from the path**: `StatePath.parentOf(p)` = text before the last `/` (`"/A/B"` → `"/A"`; `"/A"` and `"A"` are top-level). Every sub-state is registered with `addState` like any other state. Only single-segment paths → flat chart (websocket, RCK).
- `start()` → `checkHierarchy()` rejects (ISE): a parent path that is not a registered `CompositeState`; a composite whose `getInitialStatePath()` is unregistered or not a direct child; a composite registered as a final state. The "initial must not be final" check uses `drillDown(m_initialState)` (the innermost state the start would reach).
- **Entry**: `enterDownTo(target, depth)` enters the target's ancestor chain from index `depth`, then follows `getInitialStatePath()` down to a leaf. Outer `enter()` runs first.
- **Signal selection**: private `selectTransition(signal)` asks the active states innermost-first; first non-empty wins (children have priority).
- **Transition (`executeTransition`)**: `sharedAncestorCount` = length of the shared prefix of `m_activeStateChain` and the target's ancestor chain; if the target itself is active, `sharedAncestorCount` is decremented so the target is exited and re-entered. Exit innermost-first down to `sharedAncestorCount`, run the action, `enterDownTo(target, sharedAncestorCount)`. This is "local" semantics: a composite's own transition into one of its children does not exit the composite. Final-state check is on the innermost state (`m_currentState`); a final sub-state ends the whole chart, and `exitEnclosingStates()` first exits every enclosing (composite) state innermost-first, leaving only the final state active — so composite `exit()` cleanup runs before finish listeners, symmetric with cancel. Exit failures there are logged and skipped like in cancel; a `VirtualMachineError` is rethrown (executeTransition then fails the chart).
- **Cancel**: exits every active state innermost-first; an `exit()` failure is logged, the state is dropped, outer states are still exited.
- Not supported: orthogonal regions, history states, entry/exit points, composite completion events.
- Tests: `StateChartTest` "복합 상태" and "복합 상태 구성 검증" sections.

## Termination requests: accept → callback returns → cleanup → notify

- **Callback region**: `m_callbackDepth > 0` while the chart runs user callbacks under `m_guard` — the initial `enterDownTo` in `startInGuard`, the whole of `dispatchSignal` (`selectTransition`, `executeTransition`, `onUnhandledSignal`), and the exits done by `applyPendingTermination`. Only the `m_guard` holder can be inside it.
- **Accept**: inside the region, `cancel(boolean)` (overridden; checks `m_guard.isHeldByCurrentThread() && m_callbackDepth > 0` *before* delegating, so other threads keep the parent flow), `complete()` and `fail()` only record `m_pendingTermination` (`Termination(kind, cause, exitStates)`) and return. **First request wins**: later ones are rejected (`cancel` → `false`, `complete`/`fail` → ISE). Internal sources use the same entry: an exception in a callback → `requestFailure(cause)` (exitStates unless VME), reaching a final state → `COMPLETE`, or `FAIL` with the `FailureState` cause (no exits).
- **Stop**: after every callback, `executeTransition` / `enterDownTo` / `exitEnclosingStates` / `selectAndExecuteTransition` check `isTerminating()` (`pending != null || isDone()`) and return. `enterState` always adds the state after `enter()` returns, so a state that cancelled in its own `enter()` is exited child-first by the cleanup.
- **Apply** (`applyPendingTermination`, after the region, still under `m_guard`): if `exitStates`, exit the chain innermost-first via `exitActiveStatesQuietly` — the exits **and the `notifyStarted()` below run with `m_callbackDepth` raised** (so a sync `whenStarted` listener calling `complete()` cannot override an accepted cancel) — so a termination requested from a cleanup `exit()` is rejected and cannot replace the decided one. Then notify; in `STARTING`, `CANCEL`/`COMPLETE` first call `notifyStarted()` (the parent cannot go `STARTING → CANCELLED/COMPLETED`, and its `cancel()` would wait out the cancel timeout on the starting thread itself). Returns the first `VirtualMachineError` from the exits; callers (`dispatchSignal`, `startInGuard`, `cancelWork`) rethrow it **after** the chart is settled.
- **Order guaranteed**: child `exit()` → parent `exit()` → terminal transition → finish listeners.
- `cancelWork()` (another thread's `cancel(true)`) goes through the same apply path with a `CANCEL` termination.
- **Inherited `complete(T)`** (`EventDrivenExecution.complete(result)` → `notifyCompleted`) is overridden: it rejects a result other than the context (IAE) and delegates to `complete()`. Otherwise `chart.complete(ctx)` would skip `m_guard` and the callback-region acceptance, so inside a callback the finish listeners would run before the callback returns, and from another thread the chart would finish mid-transition. The parent's `notify*` methods are still public (they are the async framework's API and the chart uses them internally); the class Javadoc tells callers not to call them. Test: `complete_with_context_inside_callback_is_applied_after_callback_returns`.
- `startInGuard`: if `notifyStarted()` returns `false` (only reachable when someone called a public `notify*` during start), the entered states are exited with `exitActiveStatesQuietly` inside the callback region (logged, VME rethrown after `notifyFailed`). Test: `start_exits_entered_states_when_finished_externally_during_start`.
- `startInGuard`: with a pending termination it applies it, rethrows a fatal start failure/cleanup VME, throws `IllegalStateException("failed to start", cause)` for `FAIL`, and returns normally for `CANCEL`/`COMPLETE`.
- `exitInnermostState()` removes the state before calling `exit()`, so an `exit()` failure never leaves it in the chain.
- `executeTransition` returns `boolean` (false = its own exception was accepted as the failure) → `SignalResult.Status.FAILED`. An exception after another termination was already accepted is only logged (result `TRANSITIONED`). A termination requested inside `selectTransition()` yields `IGNORED`.
- `addState` rejects a state whose `getContext() != m_context` (IAE).
- `dispatchSignal` rethrows **any** captured failure (`Throwables.sneakyThrow` for a sneaky checked exception from `selectTransition`/`onUnhandledSignal`), so `postSignal()`'s future never completes normally while the chart is `FAILED`. The signal executor then surfaces it as `RuntimeExecutionException` from `processSignal()` and as the future's failure from `postSignal()`.

## StateChart lifecycle

1. `new StateChart(context)` — auto-attaches itself to the context via `setStateChart`.
2. `addState(State)` × N — register all states (must be in `NOT_STARTED`).
3. `setInitialState(path)`; `addFinalState(path)` only for non-sink final states (`TerminalState`/`FailureState` become final on `addState`). Initial must NOT be final.
4. `start()` — validates (incl. `checkHierarchy()`), locks `m_guard`, calls `notifyStarting`, enters the initial state (`enterDownTo(initial, 0)` — ancestors first, then down to a leaf), transitions to `RUNNING`, calls `notifyStarted`. Failure during `enter()` → `notifyFailed(cause)` + `IllegalStateException`.
5. `handleSignal(signal)` (→ `processSignal` → queue → `dispatchSignal`) — when running, asks the active states innermost-first for a transition; if matched, runs `executeTransition` (exits → action → entries, see Hierarchy); if the innermost state afterwards ∈ `m_finalStates`, auto `complete()` (or `fail(cause)` for `FailureState`).
6. `cancel(true)` → parent moves to `CANCELLING` and calls `cancelWork()`, which exits all active states innermost-first (an `exit()` exception is logged, that state is still dropped and outer ones are exited) and then **confirms the cancel with `notifyCancelled()`** — so the chart reaches `CANCELLED`, finish listeners run, and `setTimeout()` (which calls `cancel(true)`) terminates a chart too. Lock order inside is `m_guard` → parent's `m_aopGuard`, the same as a transition reaching a final state. If a racing transition already finished the chart, `cancelWork()` leaves that result and returns `false`.

## Signal processing (queue, run-to-completion)

- Three entry points: `handleSignal(signal)` (sync, `Optional<Transition>` = `processSignal(signal).getTransition()`), `processSignal(signal)` (sync, `SignalResult` with `Status` TRANSITIONED / UNHANDLED / IGNORED / QUEUED), `postSignal(signal)` (`CompletableFuture<SignalResult>`, never completes with QUEUED).
- All three go through one FIFO queue, implemented by `utils.thread.CallerRunsSerialExecutor` (`m_signalExecutor`, constructed with `m_guard` as its **outer lock**; see [utils.thread](../thread/CLAUDE.md)). One thread at a time is the **dispatcher**: whoever enqueues into an idle chart becomes it and drains the queue to empty, processing other threads' signals too. Each signal is a `SignalTask` (named `Callable` so executor logs show the signal) that calls `dispatchSignal` under `m_guard`.
- `processSignal` = `invokeOrDefer(task)`: deferred → `QUEUED`; otherwise `Invocation.get()`, which rethrows the **original** exception to the **sender** even when another thread dispatched (a `CompletionException` thrown by a state is not unwrapped). Deferred happens when the caller is the dispatcher itself (a state callback / transition action / a future callback running on the dispatcher), **or** holds `m_guard` while another thread dispatches (that dispatcher may be blocked on `m_guard` → waiting would deadlock; e.g. a sync finish listener).
- `postSignal` = `submit(task).copy()`. **The copy matters**: the executor skips a task whose future is already done when it reaches the head of the queue, so handing out the internal future would let a caller's `cancel()` / `orTimeout()` / `completeOnTimeout()` silently drop the signal. With the copy, a posted signal is always processed; side effect: `whenComplete`/`handle` on the returned future see a `CompletionException` wrapping the original (`get`/`join` unchanged). Regression test: `posted_signal_is_processed_even_if_its_future_is_cancelled_or_timed_out`.
- `start()` = `runAsDispatcher(this::startInGuard)`: takes the dispatcher role (waits if another thread is dispatching pre-start IGNORED signals) for the whole start and drains afterwards, so signals sent during start — including from the initial `enter()` — are processed after `RUNNING` instead of being ignored. Calling `start()` while holding `getChartLock()` (outside a callback) always throws `IllegalStateException`, even when idle (it could deadlock when another thread is dispatching).
- Effect: no nested transition inside a transition (a same-thread `handleSignal` from `enter()` is queued instead of re-entering `m_guard` mid-transition), and cross-thread order = enqueue order. Lock order: `m_guard` → executor queue lock is allowed (enqueue from a callback); the executor never takes `m_guard` while holding its queue lock (tasks run after the queue lock is released).
- `setLogger` also sets the executor's logger.
- `protected onUnhandledSignal(signal)` — called under `m_guard` on the dispatcher thread when the chart is running and no active state selected a transition; exceptions are treated like a `selectTransition` exception. `WebSocketStateChart` overrides it for its fall-back (overriding `handleSignal` and checking for an empty result cannot tell QUEUED from UNHANDLED).
- Do not wait in a state callback for the future of a signal posted from that callback (it is processed only after the callback returns).
- Tests: `StateChartTest` "신호 처리 순서와 결과" section.

## Conventions

- All configuration, transitions and listener invocations are serialized through `m_guard` (a separate `Guard` from parent's `m_aopGuard`). `m_guard` is **private**; subclasses and tests use `getChartLock()`.
- Configuration methods (`addState`/`setInitialState`/`addFinalState`) run under `m_guard`, and `start()` validates (`checkConfiguration()`) inside `startInGuard()` under the same lock, right before `notifyStarting()` — so a chart configured on one thread and started on another sees the configuration, and nothing can be added between validation and start. `findState`/`getInitialState` read without the lock (configuration is immutable after start).
- **Synchronous finish listeners (`whenFinished`) run holding `m_guard` and `m_aopGuard`** on every terminal path except a pre-start `cancel()` (only `m_aopGuard`): the chart notifies the parent while holding `m_guard`, and the parent runs sync listeners inside `m_aopGuard`. Same-thread re-entry works; other threads' `handleSignal`/`getCurrentState`/`cancel` wait until the listener returns. The notification is deliberately not moved out of `m_guard`: the parent's lock would still block `handleSignal` (via `isRunning()`), and deferring the notification opens a final-state-but-`RUNNING` window where a signal hits `TerminalState.selectTransition()` and fails the chart. Pinned by `StateChartTest.sync_finish_listener_runs_while_chart_lock_is_held`.
- **Lock order is `m_guard` → `m_aopGuard`** (`start()`, a transition reaching a final state, `complete()`/`fail()`, `cancelWork()`). Never take `m_guard` while holding `m_aopGuard`. In particular `toString()` must stay lock-free on `m_guard`: the parent logs `this` inside `m_aopGuard` (`notifyFailed`, `notifyCancelled`, …), and a `toString()` that locked `m_guard` would deadlock e.g. a pre-start `cancel()` against `start()`. `m_currentState` is `volatile` for that read; writes still happen only under `m_guard`.
- `start()` (initial `enter()`), `handleSignal(...)`, `executeTransition(...)` and `cancelWork()` catch `Throwable`, so an `Error` (e.g. `AssertionError`) also fails the chart (or, in `cancelWork()`, still confirms the cancel) — same paths as `Exception`. Only `VirtualMachineError` (`OutOfMemoryError`, `StackOverflowError`, `InternalError`) is rethrown, via `throwIfFatal(...)`, **after** the chart is settled: `executeTransition` rethrows it (so `handleSignal` propagates it even though it absorbs ordinary transition failures; `handleSignal`'s catch skips the second `notifyFailed` when the chart `isDone()`), `start()` rethrows it unwrapped instead of `IllegalStateException`, and `cancelWork()` throws it after `notifyCancelled()` (it escapes `cancel()`, whose catch handles only `Exception`). Pinned by the `StateChartTest` "Error 처리" tests.
- `addState` / `setInitialState` / `addFinalState` reject calls after the chart has started (`isNotStarted()` check). `addState` also rejects a path that is already registered (`IllegalArgumentException`, first state kept) — silent replacement would leave `m_initialState`/`m_finalStates` pointing at the old object.
- **Paths** (`StatePath`): `addState` calls `StatePath.checkValid(path)` → IAE for empty, trailing `/` (incl. `"/"`), or an empty segment (`//`). Leading `/` is optional (both `"a"` and `"/A"` are used — websocket/tests use bare names). `StatePath.parentOf` / `segments` are the only path parsers.
- **Name & logging**: `getName()` / `setName(name)` (volatile; `null` resets) — default `ClassSimpleName@identityHex` computed once in the constructor **before** `setStateChart` (anonymous subclass → `StateChart@...`). Every log line is prefixed with the name; `toString()` = `name[AsyncState, state=current]`. Levels: one INFO per transition (`<name>: transition <src> -> <target>`, **no signal** — signals can be large, so the signal stays in the DEBUG "received signal" line); entered/left state, received signal, internal transition are DEBUG. `m_logger` is volatile.
- `findState(path)` returns `Optional` (empty for unknown paths) and, like `getInitialState()`, reads **without** `m_guard` (`m_states` is a `ConcurrentHashMap`, `m_initialState` volatile; writes stay under `m_guard`). Reason: a caller holding only `m_aopGuard` (a pre-start `cancel()`'s sync finish listener) would invert the `m_guard` → `m_aopGuard` order. `getCurrentState()`/`getActiveStates()` still take `m_guard` (they wait for an in-flight transition) — their Javadoc warns against calling them there. Do not add a path-taking `getState(String)`: it would overload the inherited `getState()` = execution state (`AsyncState`).
- Argument validation uses `utils.Preconditions.checkNotNull` / `checkNotNullArgument` / `checkArgument`. Korean Javadoc dominant.
- No Guava `Preconditions` are used in the package. Guava `Maps`/`Sets` are still used.
- Javadoc in `StateChart` must write `{@link utils.statechart.State}` in full — the simple name does not resolve there (the source declares the type fully-qualified throughout), and `gradle javadoc` fails with "reference not found".

## Common gotchas

- Final-state assertion: `start()` rejects if `m_initialState` is in `m_finalStates`. The chart must make at least one transition.
- `addState` makes every `TerminalState` final, so a `TerminalState` used as the initial state is rejected by "initial must not be final".
- `handleSignal(signal)` returns `Optional.empty()` for IGNORED / UNHANDLED / QUEUED alike — use `processSignal` when the difference matters. Ignored-signal logging: before start → WARN every time; after termination (or while cancelling) → first one INFO, rest DEBUG.
- `Transition.execute(...)` runs while `m_guard` is held. Long-running work in actions blocks signal processing.
- `FailureState` requires the inbound transition to populate the cause BEFORE executeTransition calls `enter` — use `Transitions.fail(path, causeFunc)`, or call `setFailureCause(cause)` in a `to(path, action)` action; otherwise the chart fails with `IllegalStateException("failure cause is not set: state=<path>")` (executeTransition substitutes it — the real cause is lost). Subclasses that keep the cause elsewhere may override `getFailureCause()`. `fail(null)` is rejected with `IllegalArgumentException` and leaves the chart running.
